## 읽는 방법

- **이력서 기반 예시:** 현재 이력서와 프로젝트 설명에 근거한 말하기 예시입니다. 본인의 실제 담당과 다르면 조정하세요.
- **기술 답변·설계 예시:** 기술적으로 설명할 수 있는 원리와 제안입니다. 실제로 적용하지 않았다면 “구현했습니다” 대신 “이렇게 설계하겠습니다”라고 말하세요.
- **본인 확인 필요:** 팀 인원, 단독 기여, 실제 장애, 지원 동기, 측정 수치처럼 자료만으로 채울 수 없는 부분입니다. 대괄호는 실제 사실을 넣기 위한 자리입니다.

첫 답변은 핵심과 한 사례로 시작하고, 세부 원리는 꼬리질문에서 풀어 주세요. 회사의 사용 규모와 본인의 개선 성과, 현재 코드와 당시 운영 코드, 구현 참여와 최종 인증 결과를 구분하는 것이 중요합니다.

## 1. 경력·기여·지원 동기

### Q01. 1분 정도로 본인을 소개해 주세요.

**답변 예시 · 이력서 기반**

“2022년부터 로지브라더스에서 사용자 서비스와 운영 도구를 개발해 온 프론트엔드 개발자 신병우입니다. TypeScript와 Vue/Nuxt를 주로 사용했고, LMS와 Admin의 데이터 조회·역할별 진입, 파트너 웹의 학습 재개 흐름, CMS의 콘텐츠 배포를 다뤘습니다. 화면 하나를 구현하는 것뿐 아니라 사용자가 들어오고, 작업하고, 중단 후 돌아오는 흐름을 연결하는 일을 해 왔습니다. 대표적으로 Partner Web에서는 파트너별 진입 조건을 나누면서 공통 미션 화면을 재사용하도록 구현했습니다.”

**꼬리질문 답변:** “인터랙티브 콘텐츠도 담당했지만 경력 전체는 학생·교사 서비스, 관리자 도구, CMS, 파트너 웹을 포함합니다. 게임 구현 경험은 입력·상태·렌더링 문제를 다룬 경험으로 설명하고, 제 주력 직무는 제품의 프론트엔드 개발입니다.”

### Q02. 본인의 강점을 가장 잘 보여 주는 프로젝트 하나를 설명해 주세요.

**답변 예시 · 이력서 기반**

“Partner Web을 말씀드리겠습니다. 파트너별로 최초 진입 방식이 달랐고, 같은 사용자도 신규 시작인지 이어하기인지에 따라 처리할 상태가 달랐습니다. 저는 파트너별 라우팅과 신규·이어하기 상태, iframe 진행 상태 연동을 담당했습니다. 진입 조건은 구분하면서 맵과 미션 실행 화면은 재사용하도록 구성했고, 세션 만료 후에는 유효한 복귀 경로를 보존하도록 연결했습니다. 핵심은 조건을 한 화면에 계속 덧붙이기보다 진입과 실행의 책임을 나눈 점입니다.”

**꼬리질문 답변:** “사용자는 자신의 진입 상태에 맞는 화면으로 들어가고, 세션이 끊겼을 때 복구 가능한 경로로 돌아갈 수 있습니다. 운영 측면에서는 공통 미션 화면의 변경을 파트너별 복사본에 반복 반영할 필요가 줄어드는 구조입니다. 이탈률이나 작업 시간 감소 수치는 따로 측정한 근거가 있을 때만 제시하겠습니다.”

### Q03. 프로젝트 전체 성과와 본인이 직접 한 일을 어떻게 구분할 수 있나요?

**답변 예시 · 본인 확인 필요**

“서비스 전체를 혼자 개발했다는 뜻은 아닙니다. Partner Web에서는 파트너별 라우팅, 신규·이어하기 상태, iframe 진행 상태 연결이 제 담당 범위였습니다. 전체 팀은 [실제 구성]이고, 저는 [직접 설계·구현한 기능]을 맡았으며, [다른 담당자의 영역]과 구분됩니다. 제 기여는 해당 기능의 변경 내용과 PR·설계 문서·화면 동작으로 설명하겠습니다.”

**꼬리질문 답변:** FE 인원 → 백엔드와 기획 담당 → 본인의 결정 권한 → 직접 수정한 기능 순서로 답하세요. 기여율을 임의의 퍼센트로 만들기보다 “API 응답 계약은 백엔드와 합의했고, 화면의 상태 전이와 공통 컴포넌트 연결은 제가 구현했다”처럼 책임을 나누는 편이 명확합니다. 이 예시의 협업 내용도 실제 사례로 바꿔야 합니다.

**본인 확인:** 프로젝트별 팀 인원, 함께 일한 역할, 대표 PR 또는 설계 결정 한 가지.

### Q04. 900개 교육기관, 96개 콘텐츠 유형, 2,128개 파일은 어떤 의미의 수치인가요?

**답변 예시 · 이력서 기반**

“900개 이상 교육기관은 회사 서비스의 채택 규모이고, 제가 직접 기관 수를 늘렸다는 의미는 아닙니다. 96개 유형과 2,128개 파일은 기존 이력서에 기록한 콘텐츠 관리 대상 범위입니다. 제가 설명할 성과는 그 환경에서 빌드 산출물 관리와 버전 배포·롤백 흐름을 구현한 부분입니다. 서비스 규모와 제 개선 결과를 분리해서 말씀드리겠습니다.”

**꼬리질문 답변:** “현재 자료에는 같은 조건에서 측정한 작업 시간이나 성능 전후 수치가 충분하지 않습니다. 대신 전체 조회를 페이지 조회로 전환한 동작, 버전 배포·복원 가능 여부처럼 확인되는 변화를 설명하겠습니다. 정량화한다면 동일 콘텐츠의 배포 단계·소요 시간 또는 동일 목록의 전송량·표시 시간을 비교하겠습니다.”

**본인 확인:** 숫자의 집계 시점과 대상. 별도 CMS 문서의 1,986개 HTML 분석 대상과 2,128개 미션 파일은 같은 모집단으로 확인되지 않았습니다. 두 수치를 섞어 증감률을 계산하면 안 됩니다.

### Q05. 프로젝트 기간이 겹치는데, 동시에 어떤 일을 한 것인가요?

**답변 틀 · 본인 확인 필요**

“이력서의 기간은 프로젝트별 참여 기간입니다. [기간]에는 [신규 개발]을 주로 맡으면서 [기존 서비스의 유지보수 범위]를 병행했습니다. 각 프로젝트를 기간 내내 같은 비중으로 개발했다는 의미는 아닙니다. 신규 개발이 집중된 시점과 이후 운영 대응을 나누어 설명드리겠습니다.”

**꼬리질문 답변:** 실제 운영 방식을 먼저 말하고, 판단 기준으로 사용자 영향, 데이터 손상 가능성, 마감, 의존 작업을 설명하세요. 답변 예시는 “학습 진행을 막는 오류를 먼저 복구하고, 새 기능은 범위를 조정해 일정 영향을 공유했다”입니다. 이런 경험이 확인되지 않았다면 자신의 과거 행동으로 단정하지 말고 판단 기준으로 설명하세요.

**본인 확인:** 프로젝트 기간이 초기 개발만인지 유지보수까지 포함하는지, 겹치는 달에 실제로 맡았던 업무.

### Q06. Vue/Nuxt가 주력인데 React를 사용하는 팀에도 기여할 수 있나요?

**답변 예시 · 이력서 기반**

“주력 제품 개발 경험은 Vue/Nuxt이며, React는 현재 포트폴리오 제작 경험으로 구분하고 있습니다. 상태의 책임을 나누고, API의 비동기 흐름과 권한·오류 상태를 처리하는 경험은 React에서도 활용할 수 있습니다. 다만 React의 렌더링과 effect, 팀이 사용하는 데이터 조회 방식은 별도로 익혀야 한다고 생각합니다. 기존 컴포넌트와 상태 관리 규칙을 먼저 읽고, 익숙한 제품 문제를 작은 기능 단위로 구현하면서 적응하겠습니다.”

**꼬리질문 답변:** “개인 포트폴리오는 React 컴포넌트·라우팅·배포를 직접 다룬 사례입니다. 다수 사용자의 인증·복잡한 상태·장기간 운영을 경험한 React 제품 경력과 같다고 말하지 않겠습니다. 전환 가능한 문제 해결 경험과 아직 검증되지 않은 React 운영 경험을 구분해 설명하겠습니다.”

### Q07. 비전공자로 개발을 시작한 계기와 부족한 기본기를 보완한 방법을 설명해 주세요.

**답변 틀 · 본인 확인 필요**

“개발을 시작한 계기는 [실제 계기]입니다. 실무에서는 [처음 부족함을 느낀 개념] 때문에 [구체적 문제]를 겪었고, [학습·실습 방법]으로 보완해 [적용 결과]를 얻었습니다. 지금은 기능을 만드는 데서 그치지 않고 브라우저와 비동기 처리 같은 기반 원리를 실제 문제와 연결해 설명하려고 합니다.”

**꼬리질문 답변:** “방송통신대학교에서는 [실제 전공·수강 과목]을 공부하고 있으며, [배운 개념]을 [실무 사례]에 연결했습니다.” 직접 연결된 사례가 없으면 수강 내용과 실무 학습을 분리해서 답하세요. 현재 자료에는 전공·수강 과목·구체적인 진학 동기가 없습니다.

### Q08. 이직하려는 이유와 다음 회사에서 하고 싶은 일을 설명해 주세요.

**답변 틀 · 본인 확인 필요**

“현재 회사에서는 사용자 서비스부터 운영 도구, 콘텐츠 배포까지 여러 영역을 경험했습니다. 다음에는 [본인이 원하는 업무 범위]에서 [더 깊게 맡고 싶은 책임]을 쌓고 싶습니다. 이번 공고의 [실제 요구사항]이 제가 경험한 [프로젝트의 문제]와 연결되어 지원했습니다.”

**꼬리질문 답변:** 공고의 요구사항 하나와 본인의 사례 하나를 연결하세요. 예를 들어 운영 화면이 중요하다면 LMS 목록 조회와 역할별 접근 경험을, 콘텐츠 제품이라면 iframe 통신과 배포 분리 경험을 설명할 수 있습니다. 지원 회사가 정해지지 않은 현재 단계에서는 제품 상황이나 이직 사유를 대신 만들어 넣지 않습니다.

## 2. Codmos Partner Web

### Q09. 파트너마다 화면을 복제하지 않고 동적 라우팅을 사용한 이유는 무엇인가요?

**답변 예시 · 이력서·프로젝트 문서 기반**

“파트너별로 인증과 시작 조건은 달라도 학습 맵과 미션을 실행하는 기능은 공통이었습니다. 화면을 통째로 복제하면 같은 수정이 여러 곳에 필요해서, URL의 파트너 식별과 진입 처리를 공통 실행 화면에서 분리했습니다. 일반적인 체험 경로에서는 partnerKey와 contentSlug를 사용하고, 파트너 정책에 따라 시작 화면과 목적지를 결정했습니다.”

**꼬리질문 답변:** “모든 파트너의 URL과 진입을 동일하게 만들지는 않았습니다. 현재 문서에는 프로필을 입력하는 신규·이어하기 체험과, 외부 일회용 토큰을 교환하는 SSO 진입이 함께 있습니다. SSO 파트너는 contentSlug가 없는 짧은 경로도 사용합니다. 차이는 진입 계층에서 처리하고, 맵·미션·iframe 실행 계층을 재사용하는 구조입니다.”

### Q10. partnerKey와 contentSlug는 어디서 검증하며, 검증이 실패하면 어떻게 처리하나요?

**답변 예시 · 경험과 설계 기준**

“URL은 외부 입력이므로 파트너 식별자와 콘텐츠가 존재하는지, 현재 파트너에서 사용할 수 있는 조합인지 확인해야 합니다. 프론트에서는 잘못된 경로로 다음 API나 실행 화면에 진입하지 않도록 검증하고, 실패 이유에 맞게 안내하거나 정상 진입점으로 이동시킵니다. 실제 접근 가능 여부는 서버에서 로그인 상태와 사용자·파트너·콘텐츠의 관계를 검증해야 합니다.”

**꼬리질문 답변:** “형식 검증은 올바른 모양의 값인지, 존재 검증은 실제 대상이 있는지, 권한 검증은 현재 사용자가 접근해도 되는지를 확인합니다. 서로 다른 검사입니다. 올바른 UUID나 slug를 안다고 해서 다른 기관의 데이터에 접근할 수 있어서는 안 됩니다.” [OWASP 권한 검증](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

### Q11. 신규 시작, 이어하기, 세션 만료 후 재방문 흐름을 설명해 주세요.

**답변 예시 · 프로젝트 문서 기반**

“체험 진입에서는 먼저 서버에 현재 세션과 진입 상태를 확인합니다. 신규 이용자는 프로필을 검증한 뒤 NEW로 시작하고, 기존 체험이 유효하면 CONTINUE로 시작하면서 학생 정보를 다시 확인합니다. 세션 만료로 시작 화면에 돌아온 경우에는 검증해 보관한 보호 경로를 우선 복구하고, 일반적인 이어하기는 코스 화면으로 연결합니다. SSO 파트너는 외부 토큰을 교환하는 별도 진입을 거칩니다.”

**꼬리질문 답변:** “이어하기가 항상 마지막 미션으로 직행하는 것은 아닙니다. 세션 만료로 저장한 복귀 경로가 있는지에 따라 다릅니다. 새로하기에서는 기존 체험 시작 시각과 마지막 맵 위치 같은 클라이언트 상태를 제거하고 NEW 흐름을 다시 시작합니다. 서버의 모든 학습 기록을 프론트가 임의로 삭제한다는 뜻은 아닙니다.”

### Q12. 서버, Pinia 또는 Nuxt state, cookie, localStorage에는 각각 어떤 상태를 두나요?

**기술 답변 · 프로젝트 문서와 설계 기준**

“인증과 학습 기록의 유효성은 서버를 기준으로 판단하고, 화면 간 공유 상태는 store나 Nuxt state에 둡니다. 새로고침 후 복구가 필요한 일부 값은 수명과 범위를 정해 저장합니다. 현재 Partner 문서에는 학생 정보의 메모리 상태와 localStorage 캐시, classroom 식별자와 복귀 경로의 cookie 사용이 나옵니다. 저장소에 값이 있다는 이유만으로 인증이나 권한이 유효하다고 판단하지는 않습니다.”

**꼬리질문 답변:** “파트너 전환 시 이전 파트너의 학생·코스·세션 상태가 섞이지 않게 제거하거나 파트너별로 구분합니다. 복구한 캐시는 서버 응답으로 다시 확인하고, 불일치하면 갱신합니다. 사용자·파트너·콘텐츠 범위와 만료 기준이 없는 전역 캐시는 피하겠습니다.”

**본인 확인:** 실제 cookie의 HttpOnly·Secure·SameSite 설정과 토큰 수명은 별도 확인 대상입니다. 문서에 cookie라고 되어 있다는 이유로 보안 속성이 설정됐다고 말하면 안 됩니다.

### Q13. 콘텐츠를 직접 컴포넌트로 넣지 않고 iframe으로 실행한 이유는 무엇인가요?

**답변 예시 · 이력서 기반**

“콘텐츠의 제작 환경이 Vue 2·Vue 3·Nuxt·정적 HTML 등으로 달랐습니다. 서비스가 각 콘텐츠의 프레임워크와 빌드 환경을 직접 의존하면 배포 결합이 커집니다. 정적 콘텐츠 URL을 iframe에서 실행하고, 학습 정보와 진행 상태는 정해진 메시지로 교환하도록 해서 서비스와 콘텐츠의 배포를 분리했습니다.”

**꼬리질문 답변:** “iframe 크기와 스크롤, 포커스·키보드 이동, 로딩·오류 표시, 종료·다음 미션 동작, 통신 규약을 별도로 맞춰야 합니다. 실행 문맥이 분리된다고 해서 완전한 보안이나 성능 격리가 자동으로 생기는 것도 아닙니다. 각 iframe의 문서·리소스 비용과 권한 설정을 함께 고려해야 합니다.” [MDN iframe](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe)

### Q14. postMessage 통신에서 무엇을 검증해야 하나요?

**기술 답변 · 설계 기준**

“보낼 때는 대상의 정확한 targetOrigin을 지정하고, 받을 때는 event.origin이 허용한 origin인지 확인합니다. 이어서 event.source가 현재 연결한 iframe의 contentWindow인지, 메시지 type과 payload가 예상한 형식인지 검사합니다. 현재 미션·실행 세션과 관련된 메시지인지도 확인해야 이전 iframe의 늦은 메시지를 구분할 수 있습니다. 검증을 통과한 메시지만 상태 변경이나 API 호출로 연결합니다.”

**꼬리질문 답변:** “origin만 맞아도 같은 출처의 다른 창에서 온 메시지일 수 있어 source와 데이터 검증이 필요합니다. targetOrigin을 `*`로 두면 대상 창이 다른 출처로 이동했을 때 의도치 않은 상대에게 정보를 보낼 수 있습니다. CORS 허용 여부와는 별개입니다.” [MDN postMessage](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage)

**본인 확인:** 메시지별 origin·source·payload·세션 검사를 실제로 어디까지 구현했는지는 코드와 연결해 말하세요. 여기의 전체 검증 목록은 기술 답변이며 구현 완료 목록이 아닙니다.

### Q15. iframe에서 준비·완료 메시지가 늦게 오거나 중복해서 오면 어떻게 처리하나요?

**기술 답변 · 설계 예시**

“부모 화면에서 현재 미션과 iframe 실행 세션을 구분하고, 준비 전·실행 중·완료 상태별로 허용할 메시지를 정하겠습니다. iframe load만으로 내부 메시지 수신 준비가 끝났다고 가정하지 않고 준비 확인 절차를 둡니다. 이전 실행의 메시지는 제외하고, 같은 완료 이벤트를 반복 수신해도 같은 작업을 다시 시작하지 않게 처리하겠습니다. 저장 실패와 완료 화면 표시도 분리해서 재시도할 수 있게 하겠습니다.”

**꼬리질문 답변:** “프론트의 중복 방지만으로는 부족합니다. 재전송이나 여러 탭에서도 중복이 생길 수 있으므로, 서버가 학습 세션·이벤트 식별자나 업무상 고유 조건으로 같은 기록의 중복 반영을 막아야 합니다. 프론트는 중복 요청을 줄이고, 서버는 데이터의 일관성을 보장해야 합니다.”

### Q16. 미션 화면에서 로딩, 빈 데이터, 네트워크 오류, 세션 만료를 어떻게 구분하나요?

**답변 예시 · 프로젝트 문서와 설계 기준**

“데이터를 기다리는 상태, 정상 응답에 실행할 콘텐츠가 없는 상태, 통신이 실패한 상태, 인증을 복구해야 하는 상태를 나눕니다. Partner 문서에서는 일반 API 오류는 공통 오류 모달로, 세션 만료는 별도 안내와 재진입 흐름으로 처리합니다. 미션 상세를 못 받은 것과 상세는 받았지만 iframe 준비가 끝나지 않은 것도 구분해야 사용자가 할 수 있는 다음 행동이 명확해집니다.”

**꼬리질문 답변:** “항상 iframe 새로고침으로 해결되지는 않습니다. 상세 조회 실패라면 API 재조회, 토큰 만료라면 인증 복구, 일시적인 콘텐츠 실행 오류라면 iframe 재시작이 필요할 수 있습니다. 기록 저장 중이라면 중복 저장 없이 복구할 수 있는지도 봐야 합니다. 재시도는 실패한 단계에 맞춰야 합니다.”

### Q17. 로그인 또는 세션 복구 후 돌아갈 경로를 저장할 때 무엇을 주의하나요?

**기술 답변 · 설계 기준**

“복귀 경로도 신뢰할 수 없는 입력으로 취급합니다. URL을 기준 origin에 대해 해석한 뒤 허용한 origin과 내부 경로인지, 현재 파트너·콘텐츠에 맞는지 확인하겠습니다. 유효 기간을 짧게 두고 사용 후 제거하며, 검증 실패 시 안전한 시작 화면으로 보냅니다. 인증 토큰이 담긴 callback URL 자체를 그대로 복귀 경로에 저장하지는 않겠습니다.”

**꼬리질문 답변:** “`/`로 시작하는지만 보면 `//외부도메인` 같은 값을 놓칠 수 있습니다. 인코딩과 정규화 후의 URL을 검사하고, 문자열 접두어만 비교하지 말고 origin과 허용 경로를 구분해서 확인해야 합니다. 서버에서 사용하는 redirectTo도 별도로 검증해야 합니다.” [OWASP 리다이렉트 검증](https://cheatsheetseries.owasp.org/cheatsheets/Unvalidated_Redirects_and_Forwards_Cheat_Sheet.html)

### Q18. Nuxt에서 iframe, window, localStorage를 사용할 때 주의할 점은 무엇인가요?

**기술 답변**

“SSR을 사용하면 서버에는 window나 localStorage가 없으므로 브라우저 API를 서버 렌더링 중에 실행하지 않아야 합니다. DOM과 연결되는 iframe 리스너는 클라이언트 생명주기에 등록하고 화면을 떠날 때 해제합니다. 브라우저 저장소를 읽기 전의 초기 화면과 서버가 만든 HTML이 달라지지 않게 해야 합니다. 민감한 사용자 상태를 서버 모듈의 공용 변수에 보관해 요청 간 공유하는 것도 피해야 합니다.”

**꼬리질문 답변:** “Nuxt는 SSR·사전 렌더링·클라이언트 렌더링 등 구성을 선택할 수 있으므로 Nuxt 사용 자체가 SSR을 뜻하지는 않습니다. hydration mismatch는 서버 HTML과 클라이언트의 초기 렌더 결과가 다른 경우 생깁니다. 로컬 저장 값, 시간·난수, 브라우저 전용 분기 등이 원인이 될 수 있습니다.” [Nuxt 렌더링](https://nuxt.com/docs/4.x/guide/concepts/rendering)

**본인 확인:** 담당 서비스의 실제 SSR 설정. 이 답변의 원리를 설명하는 것과 SSR을 운영했다는 주장은 다릅니다.

## 3. Codmos CMS·콘텐츠 배포

### Q19. Vue 2·Vue 3·Nuxt·정적 HTML 콘텐츠를 어떻게 같은 배포 흐름으로 관리했나요?

**답변 예시 · 이력서 기반**

“콘텐츠의 소스 코드를 모두 같은 프레임워크로 바꾸기보다, 실행 가능한 정적 산출물과 메타데이터를 관리 단위로 삼았습니다. 콘텐츠 유형별 빌드 결과를 판별해 배포하고, 서비스에서는 그 결과의 URL을 iframe으로 실행합니다. 이렇게 하면 서비스가 각 콘텐츠의 소스 구조와 의존성까지 알 필요가 줄어듭니다. 공통화한 것은 제작 기술 자체보다 빌드 결과를 관리하고 전달하는 절차입니다.”

**꼬리질문 답변:** “Node 서버 실행이 필요한 산출물은 정적 파일 배포만으로 동작하지 않습니다. 해당 콘텐츠를 정적으로 생성할 수 있는지 확인하거나 서버 런타임을 별도로 운영해야 합니다. Nuxt를 사용했다고 해서 모든 빌드 결과를 S3에 그대로 올릴 수 있는 것은 아닙니다.”

**본인 확인:** 콘텐츠 유형별 실제 출력 디렉터리와 엔트리 판별 규칙 한 가지씩을 준비하세요.

### Q20. npm Workspaces를 사용한 이유와 한계를 설명해 주세요.

**답변 예시 · 경험과 기술 원리**

“한 저장소에서 여러 콘텐츠 패키지를 관리하고 패키지 간 연결과 작업 실행을 정리하기 위해 Workspaces를 사용했습니다. 저장소 안의 패키지 설치·연결을 도와주지만, 서로 다른 Vue 버전을 자동으로 호환시켜 주거나 모든 빌드를 자동으로 최적화해 주는 도구는 아닙니다. 각 패키지의 의존성과 빌드 결과는 여전히 구분해서 관리해야 합니다.” [npm Workspaces](https://docs.npmjs.com/cli/v11/using-npm/workspaces/)

**꼬리질문 답변:** “Workspaces는 패키지 관리 방식입니다. 그것만으로 런타임의 독립성이나 마이크로 프론트엔드 구조가 성립하지는 않습니다. 제 사례의 배포 분리는 콘텐츠의 정적 산출물·URL·메시지 계약을 서비스와 분리한 데서 나옵니다. 별도 런타임 조합 기술을 사용했다고 확대해서 설명하지 않겠습니다.”

### Q21. 서비스와 콘텐츠의 ‘독립 배포’가 가능해진 구조를 설명해 주세요.

**답변 예시 · 이력서 기반**

“서비스가 콘텐츠 소스 코드를 직접 포함하는 대신, 배포된 콘텐츠 URL을 실행하고 필요한 데이터를 메시지로 주고받게 했습니다. 콘텐츠의 수정은 해당 콘텐츠 산출물과 배포 이력으로 관리할 수 있고, 서비스 코드 수정과 배포를 매번 동반할 필요가 줄어듭니다. CMS에서는 콘텐츠명과 버전을 기준으로 배포·복원 대상을 관리했습니다.”

**꼬리질문 답변:** “통신 계약이 호환되는 범위에서 독립 배포가 가능한 것입니다. 필수 메시지나 payload 의미가 깨지면 서비스도 대응해야 합니다. 앞으로 확장한다면 메시지·메타데이터의 버전을 구분하고, 기존 필드는 유지하면서 선택 필드를 추가하는 방식부터 검토하겠습니다. 호환성 시험과 지원 기간도 필요합니다.”

### Q22. 같은 콘텐츠 버전의 중복 배포와 배포 중 일부 파일만 올라간 상태를 어떻게 다루나요?

**답변 예시 · 확인된 구현과 추가 설계 구분**

“현재 CMS 매뉴얼에는 같은 콘텐츠의 이미 존재하는 버전으로는 배포할 수 없고, 버전 목록을 보여 주는 동작이 명시되어 있습니다. 다만 중복 버전 검사만으로 여러 파일의 배포가 원자적으로 완료된다고 말할 수는 없습니다. 부분 업로드까지 개선한다면 별도 버전 경로에 업로드·검증을 마친 뒤 서비스가 참조하는 배포 버전을 전환하겠습니다.”

**꼬리질문 답변:** “존재 여부 확인과 생성 사이에 다른 배포가 들어올 수 있습니다. 배포 단위 잠금이나 저장 계층의 조건부 생성 등으로 경쟁 상황을 처리해야 합니다. S3의 단일 객체 조건부 쓰기는 기존 객체 덮어쓰기를 막는 수단이지만, 여러 파일 전체를 한 번에 성공·실패시키는 트랜잭션과 같지는 않습니다.” [AWS S3 조건부 쓰기](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)

**본인 확인:** 실제 중복 검사 위치, 동시 배포 제어, 실패한 배포의 정리 방식. 현재 확인한 매뉴얼만으로 모두 구현됐다고 단정할 수 없습니다.

### Q23. CDN을 사용하는데 배포 후에도 이전 화면이 보이면 무엇부터 확인하나요?

**기술 답변 · 현재 운영 흐름과 설계 기준**

“사용자가 요청한 콘텐츠 URL과 버전을 먼저 확인하고, 원본 파일·CDN 응답·브라우저 캐시를 나눠 보겠습니다. HTML은 최신인데 그 안의 JS나 이미지가 이전 파일인지도 확인합니다. 현재 CMS 매뉴얼은 production 배포 시 CDN 캐시 무효화를 수행하는 흐름입니다. 무효화가 끝났다고 브라우저나 별도 프록시에 남은 캐시까지 모두 지워지는 것은 아닙니다.” [AWS CloudFront 캐시 무효화](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Invalidation.html)

**꼬리질문 답변:** “`no-cache`는 저장을 금지하는 것이 아니라 재사용 전에 재검증하도록 하는 지시이고, `no-store`는 저장하지 않도록 하는 지시입니다. 내용이 바뀌지 않는 버전·해시 URL의 파일은 길게 캐시하고, 최신 버전을 가리키는 문서나 메타데이터는 변경을 빨리 확인하도록 설계할 수 있습니다. 실제 헤더는 개인정보 여부와 운영 요구에 맞춰 정합니다.” [MDN HTTP 캐시](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)

### Q24. 콘텐츠 롤백은 어떻게 동작하며 무엇까지 되돌릴 수 있나요?

**답변 예시 · 프로젝트 매뉴얼 기반**

“CMS에서는 콘텐츠명과 버전으로 배포 이력을 관리하고, production 배포 시 버전 아카이브를 남깁니다. 문제가 생기면 특정 버전으로 production 콘텐츠를 되돌리는 절차를 사용합니다. 여기서 말하는 롤백은 배포한 콘텐츠 파일의 복원 범위입니다. 사용자 학습 기록이나 백엔드 데이터까지 자동으로 과거 상태로 돌린다는 의미는 아닙니다.”

**꼬리질문 답변:** “API가 이전 콘텐츠와 호환되지 않거나, 데이터 형식이 바뀌었거나, 캐시가 남아 있으면 파일만 복구해도 문제가 이어질 수 있습니다. 복원 후에는 실행 URL·주요 리소스·메시지 통신·학습 기록 저장까지 확인해야 합니다. 롤백 대상 버전이 현재 서버와 함께 동작하는지도 검증해야 합니다.”

**본인 확인:** 실제 장애에서 롤백을 수행한 경험과 복구 시간은 별도 사실입니다. 도구를 구성한 경험만 확인된다면 운영 장애 복구 사례로 바꾸어 말하지 마세요.

### Q25. 콘텐츠 메타데이터에는 무엇을 넣고 어디에서 검증하나요?

**기술 답변 · 설계 예시**

“실행할 콘텐츠를 식별하고 호환성을 확인하는 데 필요한 정보를 둡니다. 예를 들면 콘텐츠 식별자, 버전, 엔트리 경로, 콘텐츠 유형, 지원 언어, 메시지 규약 버전 등입니다. 빌드·배포 단계에서 필수 값과 실제 파일 존재를 확인하고, 서비스에서도 외부 데이터를 읽을 때 필요한 필드를 검증하겠습니다. 화면에 쓰는 제목과 배포 식별자처럼 목적이 다른 값도 구분하겠습니다.”

**꼬리질문 답변:** “형식의 버전을 명시하고 지원하는 버전을 판별하겠습니다. 추가 필드는 이전 소비자가 무시할 수 있도록 설계하되, 필수 값의 의미를 바꾸는 변경은 별도 버전이나 변환 계층을 고려합니다. 알 수 없는 형식을 임의로 해석하기보다 지원하지 않는 콘텐츠로 안내하는 편이 예측 가능합니다.”

**본인 확인:** 위 필드 목록은 설계 예시입니다. 현재 메타데이터의 실제 필드와 혼동하지 마세요.

### Q26. 콘텐츠 이름이나 업로드 경로를 파일 경로로 사용할 때 무엇을 검증해야 하나요?

**꼬리질문 답변:** “`../` 제거만으로는 충분하지 않습니다. 절대 경로, 다른 구분자, 인코딩·정규화, 링크를 통한 우회처럼 입력 표현이 달라질 수 있습니다. 허용한 식별자로 서버가 경로를 생성하고 최종 대상 범위를 검증하는 방식이 필요합니다.” [OWASP 경로 이탈](https://owasp.org/www-community/attacks/Path_Traversal)

**본인 확인:** 이력서의 URL 검증을 서버 파일 경로 공격까지 완전히 방어한 경험으로 확대하지 마세요.

### Q27. Puppeteer로 HTML 리소스를 수집하고 CDN 경로로 바꾸는 과정을 설명해 주세요.

**답변 예시 · 이력서 기반**

**꼬리질문 답변:** “추가 검증을 설계한다면 스크롤이나 특정 화면 진입 뒤 생기는 지연 로딩 리소스, CSS의 url과 폰트, 상대 경로의 기준 URL을 확인하겠습니다. 실패한 리소스를 빈 경로로 조용히 바꾸지 않고 실패 목록과 재시도 결과를 남깁니다. 변환한 HTML을 원본 외부 주소에 의존하지 않는 환경에서 열어 누락을 확인하겠습니다.”

**본인 확인:** 지연 로딩·CSS·폰트까지 현재 수집기가 지원하는지, 수집 대상의 사용 권한과 외부 의존성을 어떻게 확인했는지.

### Q28. 이미지 URL 만료와 base64 용량 문제를 어떻게 해결했나요?

**답변 예시 · 이력서 기반**

“원본의 만료되는 URL을 그대로 참조하지 않고 리소스를 별도 파일로 관리하는 CDN 주소로 치환했습니다. 큰 이미지를 HTML 안에 base64로 모두 넣는 대신 문서와 리소스를 분리하면 파일별 캐시와 재사용을 할 수 있습니다. 다만 URL을 옮기는 것만으로 영구 보관이나 성능 향상이 자동으로 보장되는 것은 아니어서, 저장 정책과 캐시 설정도 함께 봐야 합니다.”

**꼬리질문 답변:** “일반적인 패딩 포함 base64 문자열은 n바이트를 `4 × ceil(n / 3)`개의 문자로 표현해, 큰 입력에서는 원본 바이트보다 약 33% 늘어납니다. data URL 접두어와 전송 압축 효과는 별개입니다. 아주 작은 리소스는 인라인이 요청을 줄일 수 있어, 크기·재사용·캐시 여부를 보고 판단합니다.” [RFC 4648 Base64](https://www.rfc-editor.org/rfc/rfc4648.html)

### Q29. 전체 조회에서 서버 페이지네이션으로 바꾼 이유를 설명해 주세요.

### Q30. offset 페이지네이션과 cursor 페이지네이션은 어떻게 다른가요?

**기술 답변**

“offset 방식은 정렬한 결과에서 일정 개수를 건너뛰고 가져오는 방식이라 페이지 번호 이동을 구성하기 쉽습니다. 다만 큰 offset은 건너뛸 행을 처리하는 비용이 커질 수 있습니다. cursor 방식은 마지막으로 본 정렬 위치를 기준으로 다음 데이터를 가져오며 연속 탐색에 적합합니다. 임의 페이지 이동과 총 페이지 수가 중요한 관리자 화면에서는 요구사항에 따라 offset을 선택할 수도 있습니다.” [PostgreSQL LIMIT·OFFSET](https://www.postgresql.org/docs/current/queries-limit.html)

**꼬리질문 답변:** “동일한 정렬 값이 여러 개일 수 있으므로 시간과 고유 ID처럼 순서를 결정하는 기준이 필요합니다. cursor를 써도 정렬 키가 수정되거나 데이터가 삭제되면 결과가 달라질 수 있습니다. 일관된 시점이 중요한 경우에는 조회 범위나 스냅샷 정책까지 서버와 정해야 합니다. cursor 자체가 모든 누락·중복을 보장해 주는 것은 아닙니다.”

**본인 확인:** 실제 프로젝트가 사용한 방식과 파라미터. cursor를 사용한 근거는 현재 이력서에 없습니다.

### Q31. 검색 조건, 정렬, 현재 페이지를 어떤 관계로 관리하나요?

**기술 답변 · 설계 예시**

“검색 조건·정렬·페이지를 하나의 조회 조건으로 보고 API 요청과 화면 표시가 같은 값을 참조하도록 하겠습니다. 필터나 정렬이 바뀌면 이전 페이지 번호가 유효하지 않을 수 있어 보통 첫 페이지로 되돌립니다. 페이지 크기가 바뀔 때도 같은 원칙을 적용합니다. 입력 중인 검색어와 실제 조회에 적용된 검색어는 필요하면 구분하겠습니다.”

**꼬리질문 답변:** “공유와 복원이 필요한 조건은 URL query에 직렬화하고, 새로 진입할 때 값의 형식·범위를 검증해 복원합니다. 기본값과 잘못된 값의 처리도 정합니다. 민감한 검색 내용은 URL·로그에 남을 수 있으므로 모든 입력을 무조건 query에 넣지는 않겠습니다.”

### Q32. 검색 요청 A보다 나중에 보낸 B가 먼저 끝나면 어떻게 처리하나요?

**기술 답변 · 설계 예시**

“마지막으로 시작한 유효한 조회만 화면에 반영하도록 요청 번호나 조회 조건 식별자를 비교하겠습니다. 가능하면 이전 요청을 AbortController로 취소해 불필요한 처리를 줄입니다. 늦은 요청의 성공뿐 아니라 실패와 finally도 현재 목록의 오류·로딩 상태를 덮어쓰지 못하게 해야 합니다. 화면을 떠났을 때도 같은 정리 규칙을 적용합니다.” [MDN AbortController](https://developer.mozilla.org/en-US/docs/Web/API/AbortController)

**꼬리질문 답변:** “debounce는 짧은 시간에 발생한 입력을 묶어 요청 횟수를 줄이는 방법입니다. 이미 보낸 요청들의 완료 순서를 보장하지 않으므로 응답 경합 처리는 별도로 필요합니다. 취소도 서버의 처리나 부작용을 되돌리는 트랜잭션은 아닙니다.”

**본인 확인:** 실제로 취소나 요청 번호를 적용한 위치가 없다면 개선 설계로 답하세요.

### Q33. 목록의 초기 상태, 로딩, 빈 결과, 실패 상태를 어떻게 설계하나요?

**기술 답변 · 설계 예시**

### Q39. JWT의 구조와 서명, 암호화, 만료의 차이를 설명해 주세요.

**꼬리질문 답변:** “decode와 exp 확인만으로 유효성을 보장할 수 없습니다. 클라이언트의 만료 확인은 화면 안내를 돕는 용도이고, 서버가 신뢰한 알고리즘과 키로 토큰을 검증하고 실제 권한을 판단해야 합니다. exp는 일반적인 밀리초 타임스탬프가 아니라 초 단위 NumericDate라는 점도 구분합니다.” [RFC 7519 JWT](https://www.rfc-editor.org/rfc/rfc7519)

### Q41. 인증 정보를 localStorage와 HttpOnly cookie에 보관하는 방식의 차이는 무엇인가요?

**기술 답변**

“localStorage는 JavaScript가 읽을 수 있고 직접 헤더에 실어 보내는 방식 등에 사용할 수 있지만, 같은 출처에서 실행되는 악성 스크립트가 토큰을 읽을 위험이 있습니다. HttpOnly cookie는 JavaScript의 직접 읽기를 제한하지만 브라우저가 요청 조건에 따라 자동 전송합니다. 따라서 cookie를 쓰는 인증에서는 Secure·SameSite·범위 설정과 CSRF 대응을 함께 고려해야 합니다. 저장소 하나만으로 안전성을 판단하지는 않습니다.”

**꼬리질문 답변:** “HttpOnly는 토큰을 직접 읽어 가져가는 경로를 줄일 뿐 XSS 자체를 없애지 않습니다. 악성 스크립트가 사용자의 브라우저에서 인증된 요청을 실행할 수도 있습니다. CSRF도 서비스 구조에 맞춰 SameSite, 요청 origin 검증, CSRF 토큰 등으로 대응해야 합니다.” [OWASP 세션 관리](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

### Q42. AES-256-GCM의 의미와 Web Crypto API 구현 과정을 설명해 주세요.

**기술 답변 · 로컬 유틸 확인**

“AES-256은 256비트 대칭키를 사용하는 암호화이고, GCM은 암호문과 관련 데이터의 무결성을 확인하는 인증 태그를 함께 제공합니다. 확인한 유틸은 32바이트 키와 12바이트 IV를 받아 Web Crypto API에 키를 import하고, UTF-8로 바꾼 문자열을 암호화합니다. 태그 길이는 128비트이며, 결과 앞에 IV를 붙여 base64 문자열로 전달하고 복호화 때 다시 분리합니다. base64는 전달용 인코딩이지 암호화 자체가 아닙니다.”

**꼬리질문 답변:** “IV는 비밀일 필요는 없지만 같은 키로 암호화할 때마다 중복되지 않아야 합니다. 12바이트는 권장되는 길이입니다. 키 교체 주기와 IV의 유일성은 다른 문제여서, IV를 월 단위로만 바꾸며 같은 키에 재사용하는 것은 올바른 정책이 아닙니다.” [MDN AES-GCM 파라미터](https://developer.mozilla.org/en-US/docs/Web/API/AesGcmParams)

**코드 확인 메모:** 확인한 함수는 IV를 외부 인자로 받으며 내부에서 새 IV를 생성하지 않습니다. 실제 호출부에서 유일성을 보장하는지는 별도 확인이 필요합니다. 이번 검색에서는 해당 저장소의 직접 호출 위치를 확인하지 못했으므로, 운영 중 IV 재사용이 발생했다고 단정하지 않습니다. 확인 위치: [CryptoUtil](C:/workspace/sparkedu-web-main/utils/crypto.ts).

### Q43. 브라우저에서 암호화하면 무엇을 보호할 수 있고 무엇을 보호할 수 없나요?

**기술 답변**

“어떤 위협을 막으려는지 먼저 구분해야 합니다. 암호화된 데이터를 키가 없는 저장·중계 계층에서 읽지 못하게 하는 등의 목적은 있을 수 있습니다. 하지만 브라우저에서 원문과 키를 함께 다루면 그 실행 환경을 장악한 공격자에게 원문을 완전히 숨길 수는 없습니다. 클라이언트 암호화는 HTTPS, 서버 권한 검증, 키 관리, XSS 방어를 대체하지 않습니다. 키가 프론트 번들에 포함되는 공개 설정인지도 확인해야 합니다.”

**꼬리질문 답변:** “암호화가 필수인 경로에서 실패 시 원문을 반환하면 암호화된 것으로 오인하고 평문을 처리할 수 있습니다. 필요한 API를 사용할 수 없으면 해당 작업을 실패로 처리하고 사용자에게 복구 방법을 안내하는 편이 맞습니다. Web Crypto의 주요 기능은 secure context에서 사용하며, 개발용 localhost 같은 신뢰 가능한 환경은 일반 HTTP 외부 사이트와 다르게 취급될 수 있습니다.” [MDN Web Crypto](https://developer.mozilla.org/en-US/docs/Web/API/Web_Crypto_API) · [MDN Secure contexts](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Secure_Contexts)

**코드 확인 메모:** 로컬 CryptoUtil에는 `crypto.subtle`을 사용할 수 없을 때 입력 문자열을 반환하는 분기가 있고, 해당 분기 자체에 개발 모드 검사는 없습니다. 이것을 안전한 암호화 실패 처리라고 답하면 안 됩니다. 실제 적용·호출 경로는 확인이 더 필요하며, 이 질문집을 만드는 과정에서 해당 코드를 수정하지는 않았습니다.

### Q44. 인증·학습 서비스의 오류 로그에는 무엇을 남기고 무엇을 빼야 하나요?

**기술 답변 · 설계 기준**

“오류 종류, 발생 시각, 기능·경로의 식별 정보, 배포 버전, 요청 또는 추적 ID처럼 원인을 연결할 정보를 남기겠습니다. 인증 토큰, 비밀번호, 암호화 키, 민감한 입력값과 응답 본문을 그대로 기록하지는 않겠습니다. URL query나 사용자 입력에 정보가 섞일 수 있어 로그를 만드는 지점에서 최소화·마스킹 기준이 필요합니다. 로깅 실패 때문에 원래 사용자 작업이 추가로 깨지지 않게 하는 것도 고려하겠습니다.”

**꼬리질문 답변:** “허용된 내부 식별자와 요청 ID로 서버·클라이언트 로그를 연결하고, 자세한 정보가 필요한 경우 접근 권한과 보관 기간을 정합니다. 사용자 ID를 단순 해시했다고 항상 익명 정보가 되는 것은 아니므로, 추적 가능성과 개인정보 노출을 함께 검토해야 합니다.” [OWASP 로깅](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)

### Q45. CORS, postMessage, iframe sandbox, CSP는 각각 무엇을 제어하나요?

**기술 답변**

“CORS는 서버의 응답을 다른 출처의 브라우저 스크립트가 읽을 수 있는지 등을 제어하는 HTTP 기반 규칙입니다. postMessage는 다른 창·iframe과 명시적으로 데이터를 교환하는 API입니다. iframe sandbox는 해당 문서의 스크립트·탐색 등 허용 능력을 제한하고, CSP는 페이지가 로드·실행할 수 있는 자원과 임베딩 등의 정책을 설정합니다. 서로 역할이 달라 하나로 나머지를 대체할 수 없습니다.” [MDN CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS) · [MDN iframe](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe) · [MDN CSP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP)

**꼬리질문 답변:** “CORS 허용이 다른 출처 iframe의 DOM 접근을 허용하는 것은 아닙니다. 필요한 데이터는 검증한 postMessage로 전달해야 합니다. CORS는 서버의 사용자 권한 검증을 대신하지도 않습니다. sandbox 옵션도 필요한 능력만 허용해야 하며, 같은 출처 콘텐츠에 과도한 권한 조합을 주면 격리 효과가 약해질 수 있습니다.”

### Q51. 레이저가 거울에서 반사되는 경로와 충돌을 어떻게 계산하나요?

**기술 답변 · 설계 예시**

“격자 퍼즐에서는 현재 셀과 진행 방향을 상태로 두고 다음 셀로 이동하며 벽·거울·목표를 판정할 수 있습니다. 거울을 만나면 거울 방향에 따른 진행 벡터로 바꾸고 경로를 이어갑니다. 일반적인 벡터 반사는 단위 법선 n에 대해 `r = d - 2(d·n)n`입니다. 상하좌우만 움직이는 45도 거울 퍼즐에서는 방향 전환 표로 더 간단히 구현할 수도 있습니다.”

**꼬리질문 답변:** “고정된 맵에서 같은 레이저가 같은 셀에 같은 방향으로 다시 들어오면 이후 경로도 반복되므로 `(셀, 방향)` 방문 기록으로 종료할 수 있습니다. 셀만 기록하면 다른 방향의 정상 재방문을 잘못 막을 수 있습니다. 상하좌우 N×N 그리드라면 가능한 상태는 최대 4N²개이며, 각 레이저의 계산마다 방문 기록을 관리합니다.”

**본인 확인:** 현재 참고 문서는 일부 레이저 계산을 추정으로 표시하고 있습니다. 위 알고리즘은 올바른 설명 예시이며 실제 코드와 완전히 같다고 주장하지 마세요. 단면 거울 등 별도 게임 규칙도 확인해야 합니다.

### Q53. 장면 전환 후 메모리가 계속 늘거나 프레임이 떨어지면 어떻게 조사하나요?

**본인 확인:** 예전 이력서의 40→60 FPS 수치는 측정 조건을 확보하기 전에는 확정 성과로 복원하지 마세요.

## 7. Vue·Nuxt·React·웹 기본기

### Q54. Vue 3의 ref와 reactive 차이와 반응성 추적 방식을 설명해 주세요.

**기술 답변**

“reactive는 객체를 Proxy로 감싸 속성 읽기·쓰기를 추적합니다. ref는 `.value`로 값을 읽고 쓰는 형태이며 원시값과 객체를 모두 담을 수 있습니다. 기본 ref에 객체를 넣으면 내부 객체도 반응형으로 변환됩니다. Vue는 렌더링이나 반응형 효과가 읽은 의존성을 추적하고, 값이 바뀌면 관련 갱신을 예약합니다. DOM 변경은 동기적으로 매번 즉시 반영되는 것이 아니라 모아서 처리될 수 있습니다.”

**꼬리질문 답변:** “일반 reactive 객체의 원시 속성을 구조 분해하면 그 시점의 값을 지역 변수로 복사하므로 원래 속성과 연결이 끊어집니다. toRef나 toRefs로 연결을 유지할 수 있습니다. 객체 속성을 꺼냈을 때는 그 객체 자체가 반응형 Proxy일 수 있어 ‘구조 분해하면 무조건 모든 반응성이 사라진다’고 일반화하면 안 됩니다.” [Vue 반응성 기초](https://vuejs.org/guide/essentials/reactivity-fundamentals.html)

### Q55. computed, watch, watchEffect는 각각 언제 사용하나요?

**기술 답변**

“기존 상태에서 계산되는 값을 만들 때는 computed를 사용하고, 계산 중에 API 요청처럼 부수 효과를 넣지 않습니다. computed는 반응형 의존성에 따라 결과를 캐시합니다. 특정 값의 변화를 기준으로 API 요청이나 외부 동작을 실행해야 하면 watch를, 동기 실행 중 사용하는 의존성을 자동 추적하는 효과가 적합하면 watchEffect를 선택합니다. 결과가 파생값인데 watch로 별도 상태에 복사하면 상태가 어긋날 지점이 늘 수 있습니다.” [Vue computed](https://vuejs.org/guide/essentials/computed.html)

**꼬리질문 답변:** “watchEffect는 동기 실행 중 읽은 의존성을 추적하므로 첫 await 이후에 처음 읽은 상태는 자동 추적되지 않습니다. 필요한 의존성이 명확하면 watch의 source로 지정하는 편이 이해하기 쉽습니다. 이전 비동기 작업은 정리하거나 결과 반영을 제한해야 합니다.” [Vue watchers](https://vuejs.org/guide/essentials/watchers.html)

### Q56. 어떤 상태를 Pinia에 두고 어떤 상태를 컴포넌트 안에 두나요?

**기술 답변 · 설계 기준**

“여러 화면이 함께 사용하는 사용자·파트너 문맥처럼 공유 수명과 책임이 분명한 상태는 store에 두겠습니다. 한 화면의 모달 열림, 임시 입력값, 단순 선택 상태는 우선 컴포넌트에 둡니다. URL로 복원해야 하는 조회 조건, 서버가 원본인 데이터도 목적에 따라 구분합니다. 전역에 넣을지보다 누가 바꾸고 언제 버리는지가 더 중요합니다.”

**꼬리질문 답변:** “API 응답을 모두 store에 복사하면 원본과 복사본, 여러 화면의 캐시가 서로 어긋날 수 있습니다. 서버 데이터는 키·갱신·무효화 규칙을 정하고 중복 보관을 줄이겠습니다. Pinia store를 구조 분해할 때 상태는 storeToRefs로 연결을 유지하고, action과 상태의 취급 차이도 구분합니다.” [Pinia 핵심 개념](https://pinia.vuejs.org/core-concepts/)

### Q57. Nuxt의 useFetch, useAsyncData, $fetch는 어떻게 구분해서 사용하나요?

**기술 답변**

“페이지 렌더링에 필요한 HTTP 데이터를 Nuxt의 상태·SSR 전달 흐름과 함께 다룰 때 useFetch를 사용합니다. useAsyncData는 HTTP에 한정되지 않은 비동기 결과를 key와 상태로 관리할 때 사용할 수 있습니다. $fetch는 실제 요청을 실행하는 함수여서 버튼 클릭에 따른 저장처럼 이벤트 기반 동작에도 적합합니다. 도구 이름만 보고 나누기보다 초기 렌더링용 데이터인지, 사용자의 동작으로 발생하는 요청인지 구분합니다.” [Nuxt useFetch](https://nuxt.com/docs/4.x/api/composables/use-fetch) · [Nuxt useAsyncData](https://nuxt.com/docs/4.x/api/composables/use-async-data)

**꼬리질문 답변:** “setup에서 $fetch만 직접 실행하면 서버 결과를 hydration 데이터로 전달하지 않아 클라이언트에서도 다시 요청할 수 있습니다. useFetch나 useAsyncData의 payload 전달을 활용하고, key·요청 조건·설정을 일관되게 관리합니다. 다만 명시적 refresh나 반응형 조건 변경까지 모두 없어지는 것은 아니며, 요청 결과가 불필요하게 중복되는 원인을 구분해야 합니다.” [Nuxt 데이터 조회](https://nuxt.com/docs/4.x/getting-started/data-fetching)

**본인 확인:** 사용한 Nuxt 버전과 실제 조회 방식. 최신 문서의 모든 옵션을 과거 코드에 적용했던 것으로 설명하지 마세요.

### Q58. Vue와 React의 상태 변경·렌더링 방식에서 주의할 차이는 무엇인가요?

**기술 답변**

“Vue는 반응형 객체의 속성 접근을 추적하므로 해당 객체의 속성을 변경하는 방식으로 갱신을 일으킬 수 있습니다. React에서는 state를 직접 변경하지 않고 setter에 새 값을 전달하며, 컴포넌트 함수의 각 렌더가 그 시점의 state를 참조합니다. 따라서 Vue 코드의 객체 변경이나 감시 방식을 React로 문법만 바꿔 옮기면 안 됩니다. 두 환경 모두 공유 상태의 책임과 파생값을 정리해야 하지만 업데이트 모델에 맞춰 구현해야 합니다.” [React state 스냅샷](https://react.dev/learn/state-as-a-snapshot)

**꼬리질문 답변:** “React state 객체의 필드를 직접 바꾸는 대신 변경된 경로의 새 객체를 만들어 setter로 전달합니다. 이전 상태에 의존하는 연속 갱신은 함수형 updater를 검토합니다. 객체를 직접 바꾸면 React가 변경을 제대로 인식하지 못하거나 이전 렌더의 state까지 훼손하는 문제가 생길 수 있습니다.” [React 객체 state 갱신](https://react.dev/learn/updating-objects-in-state)

### Q59. React의 useEffect는 언제 필요하며 언제 쓰지 않아도 되나요?

**기술 답변**

“effect는 이벤트 구독이나 브라우저 API처럼 React 밖의 시스템과 상태를 동기화할 때 사용합니다. 기존 props·state로 계산할 수 있는 값은 렌더 중 계산하고, 특정 버튼 클릭 때문에 생기는 동작은 보통 해당 이벤트 핸들러에 둡니다. 외부 이벤트를 구독했다면 cleanup에서 해제합니다. 현재 포트폴리오의 경로 변경 시 스크롤 위치를 맞추는 동작은 브라우저 상태와의 동기화 사례입니다.” [React effect가 필요하지 않은 경우](https://react.dev/learn/you-might-not-need-an-effect)

**꼬리질문 답변:** “StrictMode는 개발 환경에서 setup·cleanup을 추가로 실행하는 검사를 통해 정리 누락 같은 문제를 드러낼 수 있습니다. 플래그로 검사를 숨기기보다 구독 해제와 자원 정리를 올바르게 구현해야 합니다. 이 동작을 production에서 effect가 항상 두 번 실행된다고 설명하면 안 됩니다.” [React StrictMode](https://react.dev/reference/react/StrictMode)

### Q60. 이벤트 루프, Promise, async/await가 화면 렌더링과 어떻게 연결되나요?

**기술 답변**

Promise의 후속 처리나 await 이후 이어지는 코드는 비동기로 예약되지만, 그 안의 계산 자체가 자동으로 다른 스레드에서 실행되지는 않습니다. 현재 작업이 끝난 뒤 microtask를 처리하는 동안에도 긴 작업이 이어지면 화면 갱신이 늦어질 수 있습니다.” [MDN microtask](https://developer.mozilla.org/en-US/docs/Web/API/HTML_DOM_API/Microtask_guide)

### Q61. TypeScript의 타입과 실제 API 응답 검증은 어떻게 다른가요?

**기술 답변**

“TypeScript는 개발·컴파일 시점에 코드의 타입 관계를 검사하지만, 서버가 보낸 JSON이 그 타입을 실제로 지키는지 자동 검증하지는 않습니다. 타입 단언으로 API 응답을 특정 타입이라고 적어도 런타임 검사가 생기지 않습니다. 외부 경계에서 필요한 필드·형식·범위를 확인한 뒤 내부에서 신뢰할 수 있는 형태로 변환해야 합니다.” [TypeScript 타입 단언](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#type-assertions)

### Q62. Vue와 React의 목록 렌더링에서 key는 왜 필요한가요?

**기술 답변**

**꼬리질문 답변:** “앞에 항목을 삽입하거나 정렬을 바꾸는 목록에서 index를 key로 쓰면 같은 위치의 컴포넌트가 다른 데이터 항목에 재사용될 수 있습니다. 입력 중인 텍스트나 펼침 상태가 다른 행에 붙는 문제가 드러납니다. 순서가 변하지 않는 단순 정적 목록과 항목 상태가 있는 동적 목록을 구분해야 합니다.” [React 목록 렌더링](https://react.dev/learn/rendering-lists)
